## 1. Dispatch preset `{{cwd}}` prompt variable removal in 0.2.1 (fatal at turn start)

- **Symptom**: Starting a turn under the `dispatch` preset on DSH 0.2.1 fails immediately with:
  `unknown prompt variable "{{cwd}}" in section "deployment:persona-prefix"; registered variables: provider, model`.
- **Harness evidence**: Commit `ab191ff20c` (`refactor: introduce workspaceworkingDirectory service`) introduced `@deepseek-ai/dsh-working-directory`, which injects a dedicated `working-directory` system-prompt section (`priority: 95`) and stopped registering the legacy `cwd` template variable on `ctx.systemPrompt` (leaving only `provider` and `model`). `renderPrompt` in `@deepseek-ai/dsh-system-prompt` throws whenever any prompt section contains an unregistered `{{variable}}`.
- **Bridge** (`presets/dispatch/agent.cordis.yml`, `src/host/agent-preset.ts`):
  - Removed the duplicate `Your working directory is {{cwd}}.` line from `persona.config.prefix` (which duplicated `persona.config.suffix` even on older generations).
  - Added `resolveDispatchPreset(resolves)` in `src/host/agent-preset.ts`: when `@deepseek-ai/dsh-working-directory` resolves (`>=0.2.1`), `persona.config.suffix` (`Your working directory is {{cwd}}.`) is omitted from the registered preset because the `working-directory` plugin already contributes the working directory section. On `0.1.7–0.2.0` (where `@deepseek-ai/dsh-working-directory` does not exist) and on `≤0.1.6` (disk sync via `DISPATCH_PRESET_YAML`), `suffix: 'Your working directory is {{cwd}}.'` is preserved intact.
- **Tests**: `test/agent-preset.test.ts` verifies both the `<0.2.1` preservation and the `>=0.2.1` stripping, and renders the resolved preset through the real `@deepseek-ai/dsh-system-prompt` `assemble()` + `renderPrompt()` pipeline with only `provider` and `model` variables registered.

## 2. `WebRuntime.Config` `searchProvider` / `fetchProvider` wrapped in `Volatile<string>` in 0.2.1-rc.2 (behavioural)

- **Harness evidence**: Commit `fda98dadd2` (`fix(web): Make searchProvider and fetchProvider config volatile (#360)`, in `dsh-v0.2.1-rc.2`) changed `packages/tools/web/src/index.ts` from `searchProvider: z.string().default('builtin')` to `searchProvider: z.string().volatile().default('builtin')` (and likewise for `fetchProvider`). At runtime on `@deepseek-ai/cordis@4.0.6`, `fiber.config.searchProvider` is a `Volatile` callable wrapper exposing `.get(): T` instead of a plain string, and `dsh-web` now hot-reads the volatile getter on each call without needing a fiber restart.
- **Impact without bridge**: `SearchProviderSwitcher.#runningProvider()` in `src/host/search-provider-switcher.ts` checked `typeof current === 'string'`, which returned `undefined` on `0.2.1-rc.2`. Consequently, every `select()` call saw `applied === false` and unnecessarily forced a full `@deepseek-ai/dsh-web` fiber restart (`scope.update(nextConfig, true)`).
- **Bridge** (`src/host/search-provider-switcher.ts`): Added `runningProviderValue(value)` which returns `value` when it is a plain string (`≤0.2.1-rc.1`) and unwraps `value.get()` when it is a Cordis `Volatile` object (`>=0.2.1-rc.2`).
- **Tests**: `test/search-provider-switcher.test.ts` covers `Volatile`-wrapped `fiber.config.searchProvider` on both `status()` and `select()`, verifying that hot updates complete without forcing a fiber reload.
