**0.1.7-rc.2** (`next`; npm dist-tags: latest `0.1.5-rc.3`, next `0.1.7-rc.2`,
alpha `0.1.7-alpha.2`). Every harness fact below was read from
`C:\Users\A\Documents\deepseek-harness` at tag `dsh-v0.1.7-rc.2` (`git show
<tag>:<path>`); the checkout's HEAD is `477b4f4205`, which **is** the rc.2 tag
(the merge of `rel/dsh-0.1.7-rc.2`), `packages/boot/app-boot/package.json` reads
`0.1.7-rc.2`, and `dsh --version` on this machine answers `0.1.7-rc.2`.

The window `dsh-v0.1.7-rc.1..dsh-v0.1.7-rc.2` is 346 commits over 3429 files.
Filtering to the twenty packages this plugin imports leaves **six with a source
delta** (`dsh-llm`, `dsh-tools`, `ui-model-selection`, `ui-tool`,
`ui-conversation`, `ui-settings`) plus `ui-locale`/`ui-chat` additions, and pure
version bumps everywhere else. **This round needed no behavioural change**: the
same source passes the same suite with byte-identical results on rc.1 and rc.2
(section 4), and rc.2's headline feature — mid-conversation tool changes — is
projected away before it can reach this plugin's adapters.

## 1. Tool-change blocks become real (`dsh-llm`) — behavioural in core, nil for us

At rc.1 the type comment in `packages/llm/llm/src/types.ts` said developer
tool-change blocks were "reserved for Session V4 persistence; providers and UI
reject them until their producers and consumers are implemented together". rc.2
implements both halves:

- **Producer** — `packages/core/agent-loop/src/agent.ts:626` appends a
  `developer/message` carrying `tool-addition` / `tool-removal` blocks whenever
  the declared tool set changes against the logged request header.
- **Consumer** — `packages/llm/llm/src/content.ts` gains `projectToolUpdates`;
  `packages/llm/llm/src/index.ts:1075` now projects messages and tools per route
  at dispatch time. New exported types: `ToolUpdate = 'in-history' |
  'addition-only'`, `LlmResolvedModelInfo.toolUpdate?`,
  `GenerateOptions.toolHistory?: ToolHistory` (`types.ts`).

**No bridge is needed, and the reason is by construction.** This plugin declares
`toolUpdate` on no route (`grep -rn "toolUpdate\|deferLoading" src` → 0 hits), so
`projectToolUpdates` takes its first branch: `withoutDeveloperMessages(messages)`
plus `deferLoading` stripped from every tool. Our mappers therefore keep
receiving the **complete current tool list with no developer messages** — the
same content rc.1 delivered, since rc.1 had no producer for those blocks either.
The same gate appears at `agent.ts:394`, where `startsSeries` became
`startsSeries || … || (preparedCall?.toolUpdate === undefined && this.toolsChanged(assembly.tools))`:
with `toolUpdate` undefined the rc.1 behaviour (a tool-set change starts a new
request series) is preserved exactly.

Adopting `toolUpdate` would let this provider cache a stable prefix across tool
changes; that is an optimisation with a wire contract to verify per route, not a
fix. Not adopted. Note the plugin's own suite **cannot see this seam at all** —
the projection happens in `LlmRuntime`, above the adapter, so a unit test that
calls a mapper directly can never exercise it.

## 2. GUI selection now requires catalog membership — behavioural, no code change

rc.2 turns the model catalog from advisory into a gate:

- `packages/api/session-controller/src/catalog.ts` adds
  `modelAvailable(ctx, selection)`: the provider must be in `llm.listProviders()`
  **and** `await llm.listModels(provider)` must contain the exact model id.
  `commands.ts` calls it through a new `requireModel()` at the top of
  `selectModel` (`commands.ts:380`), failing with
  `session/model-unavailable`.
- `routableProviders` is now `groups.map(group => group.id)` — only providers
  with at least one advertised model count as routable, where it used to be the
  raw provider list.
- The send path got **more** permissive in the same commit: `sendPrompt`'s
  `routeServed(ctx, provider)` check and the whole `routeServed` function were
  deleted. Sending no longer requires an adapter for the selected provider;
  changing the model does now require catalog membership.
- Client side, `packages/client/ui-model-selection/src/client/directory.ts`
  redefines `routable` from "an adapter serves this provider" to "the current
  selection is present in the available catalog", and
  `ModelDirectoryResolver` lost its `blockReason` config and its
  `conversation.blocks` publish — the composer is no longer made inert when a
  selection leaves the catalog.

**What this means for the plugin:** every route here already advertises what it
offers (`listCodexModels` filters the shipped `CODEX_MODEL_CATALOG` by
`visibleModelIds`; antigravity reads a shipped `MODELS` table; zhipu falls back
to `FALLBACK_MODELS` when signed out), so selection keeps working offline for
Codex, antigravity and signed-out zhipu. For the three routes whose `catalog()`
reads a remote list — `command-code`, `kimi-code`, `workbuddy` — a model change
while that fetch is failing now fails at `selectModel` where rc.1 allowed it.
That is the same failure shape the Codex persisted-snapshot commit (`8aecca0`)
already addressed for the primary route, and it is the harness's deliberate
choice; **no bridge was added**, because weakening a gate the harness just
introduced is exactly the kind of "simplification" the skill warns about. Left
as an observation for the maintainer.

`ModelDirectoryState` gained a **required** `pending` field and an optional
`retainedEffort`. The plugin only ever reads `directory.store` and never
constructs the literal (no occurrence in `src/` or `test/`), so the forced
typecheck is clean — but any future literal construction must add `pending`.

## 3. New first-party quota notice — optional capability, not adopted

- `packages/llm/llm/src/error.ts:31` adds
  `ACCOUNT_QUOTA_EXCEEDED_CODE = 'ACCOUNT_QUOTA'`. Sole producer is
  `packages/llm/llm-deepseek-account/src/index.ts:29`; consumers are
  `packages/client/ui-chat/src/client/apply.ts:90` and
  `packages/client/ui-settings-account/src/client/index.ts:247`.
- `packages/client/ui-chat/src/client/chat/QuotaNoticeHost.tsx` is **new** at
  rc.2: a frame-wide `shell.overlay` host holding one live notice for the whole
  app, with a new `shell.quota-notice` slot a plugin may register to replace the
  generic Toast for the codes it claims
  (`QuotaNoticeCode = 'QUOTA' | 'ACCOUNT_QUOTA'`, `ui-chat/…/contract/slots.ts:61`).

This plugin throws no `QUOTA` and no `ACCOUNT_QUOTA` code anywhere
(`grep -rn "ACCOUNT_QUOTA\|'QUOTA'" src test` → 0 hits), so the new surface
never fires for us and quota exhaustion stays where it is today: the composer
chips and the settings cards. Registering a `shell.quota-notice` view for
ChatGPT-subscription quota exhaustion would be a genuine UX addition, but it is
a feature, not a compatibility fix, and `ACCOUNT_QUOTA` in particular points the
user at the DeepSeek billing page, which does not apply to a ChatGPT
subscription. Not adopted.

## 4. Smaller deltas (all checked, none plugin-relevant)

- `vendor/` **byte-identical**: `git diff dsh-v0.1.7-rc.1..dsh-v0.1.7-rc.2 --
  vendor` is empty. No cordis, loader, or schemastery move this round — unlike
  alpha.1→rc.1, nothing needs re-pinning.
- Source trees **identical** (verified by tree hash, not by reading the diff):
  `packages/web/web` (`dsh-web`), `packages/host/webserver`,
  `packages/attachment/attachment`, `packages/util/timeout`,
  `packages/settings/settings`. Their only changed files are `package.json` and
  `README.i18n.yaml`.
- `packages/web/tool-web` is a **different package** (`@deepseek-ai/dsh-tool-web`,
  a dependency of the composition, not of `dsh-web`) and its rc.2 change is
  model-facing prose only — the `TOOL_WEB_FETCH` system-prompt section and the
  `web_search` description got shorter. Its `Config` is byte-identical at both
  tags, so this plugin's preset row (`src/host/agent-preset.ts`, `{ fetch: true,
  searchTimeoutMs: 60000 }`) still validates. Its `WebError` / provider
  interfaces live in `dsh-web`, which did not change.
- `packages/core/tools/src/index.ts` (`dsh-tools`): additive optional
  `displayReason` on the `ask` arm of `PreToolDecision`. `ToolGuard` is
  byte-identical and this plugin never constructs that union — it only wraps the
  guard (`src/host/subagent-model-authorization.ts`).
- `ui-tool`: additive — `ToolRowProps.href`, a new `webFetchHref()`, new
  `schedule_update` cases. The `tool.call.toolview` registration API, the slot
  declaration, and the phase union are unchanged, so the image card's
  registration is untouched.
- `ui-settings`: `SettingsLauncherOwnerProps` gained a required `settingsOpen`
  and an optional `settingsShortcut` — on `settings.launcher`, a slot this
  plugin does not register. `settings.section` is unchanged.
- `ui-conversation`: `ComposerBarInjected` gained a required
  `hooks.stopShortcut` on the **parent** `conversation.composer.bar`
  registration; `conversation.input.right` declares no `inject`, so the six
  quota chips' `PropsRuntime` is unchanged. `ConversationBinding.openTurn` was
  added and `binding()` now throws for an unknown session — our only
  `uiConversation` use is the defensive `ctx.get('uiConversation')?.imageUrl`
  probe, and our `ctx.conversation` reads sit inside a `try/catch`.
  `DEVELOPER_TOOLS_VIEW_ID` was renamed to `TRAJECTORY_VIEW_ID`; it is not
  re-exported from the client entry and not imported here. New
  `stop-shortcut.ts` / `stop-sequence.ts` scope Escape-Escape to
  `[data-conversation-session]` / `[data-conversation-region]`, which our
  mermaid view and zoom modal sit outside of.
- `ui-model-selection` internals: `catalog.ts` gains `reasoningFor()` and a
  `credentials/record-updated` refresh subscription (our credential writes now
  refresh the catalog too — harmless, arguably a benefit); `ModelSelect.tsx`
  gains a pending spinner, `MenuSurface`, and `deepseek-account` group ordering;
  the resolver's `blockReason` config was dropped (section 2).
- `ui-locale`: additive `workspace.defaultName` in both dictionaries.
- **Peer-compatibility preflight (new at rc.1) is unchanged and this plugin
  still clears it.** `packages/boot/app-boot/src/plugin-compatibility.ts:77`
  denies any profile row whose `@deepseek-ai/dsh`-prefixed peer fails
  `semver.satisfies(runtime, range, { includePrerelease: true })`. Probed for
  runtime versions `0.1.7-rc.2`, `0.1.7-rc.1`, `0.1.7-alpha.2`,
  `0.1.7-alpha.1`, `0.1.6-alpha.1`, `0.1.5-rc.3`, `0.1.2-alpha.5` → **OK on all
  seven**. The `|| ^0.1.7-rc.1` clause already covers rc.2 (same `0.1.7` tuple),
  so the new clause is for legibility — *except* that the repo's own suite makes
  it mandatory, see the next bullet.
- **The peer clause is required, not cosmetic.** `test/package-integrity.test.ts:67`
  splits the peer range on `||` and asserts every devDependency range string
  appears verbatim in it. Bumping `devDependencies` to `^0.1.7-rc.2` therefore
  **fails the suite** unless `|| ^0.1.7-rc.2` is added to the peer union. This
  was found the hard way: an early clean-room run that pinned devDeps to a bare
  `0.1.7-rc.1` failed exactly that assertion.
- **`npm install` cannot move this baseline incrementally.** With rc.2 devDeps,
  a plain `npm install` against the rc.1 lockfile dies with `ERESOLVE`:
  `@deepseek-ai/dsh-attachment@0.1.7-rc.2` pins its peer
  `@deepseek-ai/dsh-brand@0.1.7-rc.2` **exactly**, and npm will not move an
  unrelated transitive dep to satisfy a newly requested one. The lockfile was
  regenerated from a clean install (`rm -rf node_modules package-lock.json &&
  npm install`); `npm ci --dry-run` now reports "up to date". Expect this every
  time a baseline bump crosses a tuple where the harness pins internal peers
  exactly.

## 6. Left unverified

- **The rc.2 tool-update projection is not covered by this plugin's suite.** The
  projection lives in `LlmRuntime`, above the adapter, so no unit test here can
  exercise it (section 1). It was established by reading
  `content.ts`/`index.ts`/`agent.ts` at the tag. First check on a real machine:
  run a turn that adds a tool mid-conversation on a Codex route and confirm the
  Responses payload still carries the full `tools` array — a developer message
  reaching `src/host/responses-mapper.ts` would be the symptom of the projection
  not applying.
- **`modelAvailable`/`requireModel` gating was not exercised end-to-end**
  (section 2). First check: with the network down, try changing the model in a
  `command-code` / `kimi-code` / `workbuddy` session and read the refusal from
  `session/model-unavailable`.
- The compatibility preflight is still **reasoned from the harness source plus a
  local `semver.satisfies` probe**, never observed at a real boot. First check:
  `dsh` starts with the plugin enabled and stderr shows no
  `disabling profile plugin` line.
- `toolUpdate`, `shell.quota-notice`, and `ACCOUNT_QUOTA` were all deliberately
  not adopted, so nothing here exercises them.
- No run against real user data or a live provider this round; every test is
  mocked OAuth / SSE / quota, per the repo's testing rules.
