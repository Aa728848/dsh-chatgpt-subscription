# Harness 0.1.7-alpha.1

Previous plugin baseline: **0.1.5-rc.2** (`latest` at the time). Target:
**0.1.7-alpha.1** (`alpha`; `next` was 0.1.5-rc.3). Every harness fact below was read
from `C:\Users\A\Documents\deepseek-harness` at tag `dsh-v0.1.7-alpha.1`
(`git show <tag>:<path>`), and the settings claim was re-checked against the
published tarball because a symlinked profile runs stale build output.

## 1. Conversation model (behavioural)

- Tool results stopped being a content block: `ToolResultBlock` and
  `ContentBlockMap['tool-result']` are gone (`packages/llm/llm/src/types.ts`), and a
  result is now a first-class message — `createToolResultMessage` returns
  `{ role: 'tool', source: { kind: 'tool', callId }, toolCallId, content, isError }`
  (`packages/llm/llm/src/message.ts`). `Message` is a closed five-arm union
  (`system | developer | user | assistant | tool`).
- `GenerateOptions.messages` widened from `Message[]` to `RequestMessage[]`
  (`Message | RequestUserInput`), and `MessageSourceMap` lost its catch-all
  `plugin` kind (kind `tool-registry` etc. are declared by their producers).
- Introduced by `f4a32dbd0a` ("refactor(llm): flatten tool results …"), present only
  from 0.1.7 on: 0.1.6-alpha.2 still has `ToolResultBlock`.
- Without a bridge, `message.content.find(b => b.type === 'tool-result')` becomes
  permanently `undefined` and tool results leak into the Responses wire as
  `role: 'tool'` inputs instead of `function_call_output` — a silent behavioural
  break, not a type error alone.

**Bridge**: `src/host/common/llm-compat.ts` (canonical `Message`/`ContentBlock`/
`GenerateOptions`, `normalizeMessages`, `normalizeGenerateOptions`,
`OutboundContentBlock`, `PLUGIN_MESSAGE_SOURCE_KIND`). One
`normalizeGenerateOptions()` per adapter request path; mappers untouched. Emitted
blocks use `OutboundContentBlock` (the shared harness blocks minus `tool-result`),
and the plugin now declares its own `MessageSourceMap` kind instead of `plugin`
(`src/host/llm-compat.ts`, `codex-images.ts`, `kimi-code/video-tool.ts`).
`test/llm-compat.test.ts` pins both generations reaching the same canonical
conversation.

## 2. Settings API (fatal at boot when unguarded)

- `packages/settings/settings/src/index.ts` no longer exports `SettingsProvider`,
  `SettingsScope`, `SettingsRegisterOptions` or `settingsNamespace`; the `settings`
  service is `SettingsForms` (`configure`/`describe`/`update`/`replace`/`mutate`),
  and the `./invariant` subpath export is gone.
- Landed in `601d6761e4` ("feat(settings): project volatile Config through
  profile-backed forms (#4587)"), contained only by `dsh-v0.1.7-alpha.1`. The old
  `$DSH_HOME/settings.yaml` is imported once into the active profile by section id
  and renamed to `settings.yaml.imported`.
- `(settings.register as Function).call(...)` becomes a `TypeError` at activation,
  which fails the whole plugin entry.
- Confirmed against the published artifact: `npm pack @deepseek-ai/dsh-settings@0.1.7-alpha.1`
  contains `SettingsForms` and no `register`, while the profile on this machine
  symlinked the source checkout and still executed a `lib/` build exposing
  `register` — the reason the break was invisible locally.

**Bridge**: `settings-compat.ts` (local structural types + `hasRegister` +
`settingsNamespace` probe), a register-path left byte-for-byte intact, and
`file-preferences.ts` (plugin-owned JSON document, `0600`, atomic write, schema
validated) for generations without the seam. `legacy-preferences.ts` imports the
old section once — `settings.yaml` and `settings.yaml.imported` — with a
dependency-free reader for the four shapes that section uses. The four provider
stores now hydrate from their own `storages/*-models.json` instead of reporting
defaults on every start.

## 3. Agent presets (fatal at boot if shipped statically)

- `~/.dsh/.agent-presets` is no longer read at all (`packages/preset/agent-presets`
  deleted; `packages/preset/agent-preset` + `agent-preset-registry` replace it). A
  preset is an `@deepseek-ai/dsh-agent-preset` row whose `config` is
  `{id, name?, description?, order?, plugins}` and whose class calls
  `ctx.agentPresets.register(config)`.
- `packages/boot/app-boot/src/index.ts` `assertEntriesLoaded()` throws when any
  non-disabled entry has no fiber — present at `dsh-v0.1.5-rc.2` too. A static
  declaration row naming a package those generations lack would therefore make the
  harness refuse to start, and patch YAML cannot be conditional on the running
  generation.

**Bridge**: `src/host/agent-preset.ts` registers `DISPATCH_PRESET` (19 rows
transcribed from `presets/dispatch/agent.cordis.yml`, `!!js` platform tests turned
into real booleans) when `import.meta.resolve('@deepseek-ai/dsh-agent-preset')`
succeeds and `ctx.get('agentPresets')` is present, inside `ctx.effect`, with every
failure caught and logged. `preset-sync.ts` keeps the home copy for older
generations and for the fallback path (`installBundledPresets`).

## 4. Smaller deltas

- `@deepseek-ai/dsh-code-runtime` → **`@deepseek-ai/dsh-ptc-runtime`** (service too).
- Cordis **4.0.2 → 4.0.3**: `Fiber.update()` no longer returns a promise, so
  `await entry.fiber.update(...)` waits for nothing — `search-provider-switcher.ts`
  now waits on `entry.fiber?.await()` after a selection, otherwise `ctx.web` has a
  window where it is undefined. `vendor/cordis/src/reflect.ts` is otherwise
  byte-identical, which is what keeps the shaded-context inject rule (section 2 of
  the skill) unchanged across generations.
- Schemastery 3.18.2 → 3.18.3: additive (`.volatile()`, `NoInfer`); no call site
  changed.
- `dsh-web`, `dsh-tools` (`defineTool`), `dsh-host-webserver`, `dsh-attachment`,
  `dsh-timeout` and `dsh-llm/message` were otherwise source-compatible.
- `@deepseek-ai/dsh-timeout` was imported by `src/host/common/idle-watchdog.ts` but
  never declared; it is now a peer and dev dependency.

## 5. Community PRs merged in the same round

- **#12** macOS Keychain hex payloads — independent, correct, kept.
- **#14** settings guard — the four provider-store guards were right; the main
  store's in-memory fallback was replaced by the file store, and the provider
  fallbacks now hydrate.
- **#15** client `inject` trio — the reported root cause does **not** hold: a probe
  with the real Cordis 4.0.3 in a sibling-fiber layout showed a service method
  resolves `this.ctx.x` from the service's own fiber, so callers need only what they
  read. The declarations are harmless and match first-party plugins, but the fix for
  the reported `cannot get property remote.session without inject` was activation
  ordering.
