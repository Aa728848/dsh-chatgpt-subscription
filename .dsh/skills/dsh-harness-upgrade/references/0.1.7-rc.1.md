## 1. `tool.call.toolview` stage union (latent, not user-visible)

- `packages/client/ui-tool/src/client/contract/slots.ts` at `dsh-v0.1.7-rc.1`
  replaced the single `block: ToolCallBlock` with a discriminated union:
  `ToolCallPhaseProps = {phase:'preparing', block: PreparingToolCall} |
  {phase:'start', block: StartedToolCall} | {phase:'result', block: ToolResultNode}`,
  with `ToolCallOwnerProps = ToolCallCommonProps & ToolCallPhaseProps`.
- `packages/client/ui-conversation/src/client/contract/records.ts` split
  `RunningToolCall` into `PreparingToolCall` (no `argsRaw` at all) and
  `StartedToolCall` (`argsRaw`), keeping `RunningToolCall` as their union.
  `ToolResultNode` still carries `kind: 'tool-result'`, so the structural
  `'kind' in block` test for "settled" keeps working on every generation.
- Introduced by `d3086e6571` ("feat(chat): present tools in preparing, start, and
  result stages"), refined by `b66b602c72`, `b660f72d4e`, `d6fb1351b3`; only from
  0.1.7-rc.1 onward (`grep -c phase` on `slots.ts` is 0 at alpha.1, 6 at rc.1).
- The view really is dispatched during `preparing`:
  `packages/client/ui-tool/src/client/tool/ToolCallTree.tsx` computes the phase from
  the block and calls `renderSlot('tool.call.toolview', owner, {entryKey, hookContext,
  fallback})` for every stage, so a registered keyed view receives a `preparing`
  owner whose block has no arguments yet.
- `CodexImageToolView` read `block.argsRaw` on that arm. It degraded gracefully
  (`undefined` → no summary, the card still showed its running title), so **no user
  saw a break** — this is contract drift at the seam, not a regression.

**Bridge**: `src/client/CodexImageToolView.tsx` — `dispatchedArgsRaw()` reads
`argsRaw` only when the arm declares it (`'argsRaw' in block`) and returns
`undefined` while a call is preparing. Old generations take the same branch they
always did, so this is preserved by construction rather than a version check.
`test/codex-image-tool-view.test.tsx` writes each stage's wire shape literally —
preparing, start, the pre-rc.1 running shape, a settled result, an errored result,
and a non-JSON argument payload — and passes on both generations. It pins the
behaviour, not the fix: the previous code produced the same output for a preparing
block, so this file cannot distinguish the two.

### The type-level blind spot this exposed

`slots.d.ts` imports `PreparingToolCall` / `StartedToolCall` / `ToolResultNode` from
`@deepseek-ai/dsh-client-ui-chat/client`, which is **not installed here and is not a
declared dependency of `dsh-client-ui-tool`** (that package has no `dependencies`
field, only a cordis peer). With `skipLibCheck: true` in both tsconfigs, those
imports resolve to `any`, so `tsc` can neither catch nor confirm anything about the
`block` shape. Every claim in this section was established by reading the harness
source, not by types. Adding `@deepseek-ai/dsh-client-ui-chat` as a dev dependency
would make this surface real, but it is a new generation-bound dependency to keep in
sync — a decision for the maintainer, not made here.

## 2. Peer-compatibility preflight (nil blast radius, worth knowing)

- New at rc.1: `packages/boot/app-boot/src/plugin-compatibility.ts` +
  `compatibility-preflight.ts` (`prepareProfileEntries` / `prepareProfilePatches`).
  A profile row whose `@deepseek-ai/dsh*` peer does not satisfy the running runtime
  under `semver.satisfies(runtime, range, {includePrerelease: true})` is **denied** —
  `row.disabled = true`, `group = false`, and a
  `dsh: disabling profile plugin …` line on stderr. Peer metadata that cannot be
  read or validated is refused rather than admitted. Introduced by `5ea77078d6` /
  `2c67633990` (#4980), refined by `07ad70817f`.
- **This plugin is not affected.** Every declared peer satisfies `0.1.7-rc.1`: the
  existing `^0.1.7-alpha.1` clause already covers `0.1.7-rc.1`, because prerelease
  comparators match within the same `0.1.7` tuple. The `|| ^0.1.7-rc.1` clause added
  this round is for legibility, not to clear a refusal. Verified with a local
  `semver.satisfies` probe over every `@deepseek-ai/dsh-*` peer.
- The plugin also never ships a static preset row, so `assertEntriesLoaded` (trap 1
  in the skill) stays out of reach.
