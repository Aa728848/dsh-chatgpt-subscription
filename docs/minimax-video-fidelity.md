# MiniMax Code 视频理解保真度实测：**真视频的描述是准的**

**这条回答的问题**：「视频理解」能不能把一段真视频讲对？——这是这条线上**最后一个未验证的功能主张**。

**方法**：真实探针 `scripts/probe-minimax-video-fidelity.probe.ts`，把一段**内容已知的 CC0 真视频**经 MiniMax 自己的上传链路送上 `cdn.hailuoai.com`，再用 `videos_understand` 读它。

**纪律**：上传**恰好一次**、理解**恰好一次**、**不重试**、**绝不生成视频**（不花生成额度）。每一步都检查响应里有没有 `task_id`，有就立刻停。

**保密**：令牌 / 邮箱 / 账号 id / realUserID 不出现；URL 只报**形状**。

跑法：

```powershell
npx vitest run --config vitest.probe.config.ts probe-minimax-video-fidelity
```

## 0. 结论速览

| # | 问题 | 实测答案 |
| :- | :- | :- |
| 1 | 真视频能否走通上传链路 | **能**。1,128,375 字节的真实 MP4，PUT HTTP **200** |
| 2 | `cdn_url` 上的字节是否与本地一致 | **完全一致**（sha256 相同，`matches-upload=true`） |
| 3 | `results[0].success` | **true** |
| 4 | **描述准不准** | **准**。下面逐条对照，7 条断言全部与画面吻合，**编造词 0 个** |
| 5 | 与垃圾字节的结论是否矛盾 | **不矛盾，是补充**：`success` 仍是必要不充分条件；但**画面里真有信息时，模型确实读了** |

> **一句话**：`success:true` 从来不证明字节被解码——这一次不是靠它，是靠**描述的内容与素材的内容逐条对得上**。喂垃圾字节会编造，喂真视频会读对；这个功能的**核心价值主张成立**。

| 项 | 值 |

### 1.1 画面是什么（**抽帧肉眼看出来的，不是从文件名猜的**）

抽首帧（0.1 s）、中帧（2.0 s）、末帧（~4.7 s）三帧逐一查看：

- **首帧**：一朵**红色闭合花苞**，旁边是**中间绿、边缘粉紫**的肉质叶，绿色细茎，深色虚化背景（苔藓 / 土面 / 远处模糊花苞）。
- **中帧**：花苞**已开始张开**，露出内部橙红色花瓣。
- **末帧**：花**完全绽放**，橙红色花瓣摊开，**中心露出黄色雄蕊**。

客观旁证：整段饱和度单调上升（`SATAVG` 22.94 → 30.13，10 个采样点），与「花瓣张开、颜色变亮」一致。

所以素材不只是「有花」，还有**可验证的时间变化**（花开），这让「有没有真的读画面」可以被检验，而不只是关键词命中。

## 2. 第 1 步：`get_upload_url`

请求 `POST https://agent.minimax.cn/mavis/api/v1/mcp/get_upload_url`（queryKeys=[]），body：

```json
{"filename":"minimax-video-fidelity-clip.mp4","mime_type":"video/mp4","size_bytes":1128375}
```

| 项 | 值 |
| :- | :- |
| HTTP | **200**（application/json; charset=utf-8），352 ms / 794 字节 |
| 顶层 | `code:0`、`message:"ok"`、`base_resp.status_code:0`、`status_msg:"success"` |
| `content_type` | **`video/mp4`** |
| `expires_in` | 600（秒） |
| **`task_id`** | **无**（有则立即终止） |

响应形状（值已换成形状）：

| 字段 | 形状 |
| :- | :- |
| `put_url` | host=**`minimax-public-cdn.oss-cn-wulanchabu.aliyuncs.com`**，1 段，ext=mp4，pathChars=83，queryKeys=`[x-oss-additional-headers, x-oss-credential, x-oss-date, x-oss-expires, x-oss-signature, x-oss-signature-version]` → OSS V4 预签名 PUT |
| `cdn_url` | host=**`cdn.hailuoai.com`**，**4 段**，ext=mp4，pathChars=56，**queryKeys=[]（无 query）** |
| `oss_key` | `cdn-yingshi-ai-com/mcp/<user-id>/general/<ts>_<hash>.mp4` |

与上一轮 1586 字节合成文件的响应**形状完全一致**——只是 `size_bytes` 变了。

> 上一轮只测了 1586 字节，本轮证明**同一链路对 ~1.1 MB 的真实文件同样可用**。

### 3.1 回读 `cdn_url`（无鉴权 GET，免费）

| 项 | 值 |
| :- | :- |
| HTTP | **200** |
| `content-type` / `content-length` | `video/mp4` / `1128375` |
| 实际字节 | 1,128,375 |
| sha256 | **`0cd83d94...24451`——与本地文件完全相同** |

**这一步是本次判定的地基**：CDN 上的对象与「我抽帧看过的那份字节」**逐字节相同**。所以后面描述若不对，只可能是服务端读取端的问题，不可能是「传输把视频弄坏了」。

## 4. 第 3 步：`videos_understand`（唯一一次可能计费的调用）

请求 `POST https://agent.minimax.cn/mavis/api/v1/mcp/videos_understand`（queryKeys=[]），body 就是 `video-tool.ts` 上传路径发的形状：

```json
{"video_info":[{"url":"<cdn_url>","prompt":"描述这个视频里发生了什么"}]}
```

| 项 | 值 |
| :- | :- |
| HTTP | **200**（application/json; charset=utf-8），**17,170 ms** / 432 字节 |
| 顶层 | `code:0`、`message:"ok"`、`base_resp.status_code:0`、`status_msg:"success"` |
| **`task_id`** | **无** |
| `results[0].success` | **true** |
| `results[0].error` | `""` |
| `results[0].source` | **回显 `cdn_url` 本身**（形状同 §2） |
| `description` 长度 | 69 字符 |

**服务端原话（逐字，完整，未删改）**：

> 这段视频通过延时摄影展现了一朵红色小花（类似马齿苋花/太阳花）从紧闭的花苞逐渐舒展花瓣、缓缓绽放开来，最终露出中心黄色花蕊的完整开花过程。

## 5. 判定：描述**准**——逐条对照

判据不是 `success`，是**描述的内容 vs 素材的内容**。

| # | 描述的断言 | 画面事实（抽帧确认） | 判定 |
| :- | :- | :- | :- |
| 1 | 一朵**红色小花** | 画面主体就是一枝大红橙色花 | **正确** |
| 2 | 从**紧闭的花苞**开始 | 首帧（0.1 s）确是红色闭合花苞 | **正确** |
| 3 | 花瓣**舒展、缓缓绽放** | 末帧（~4.7 s）花瓣完全张开；饱和度 22.94→30.13 | **正确，且是时间性的** |
| 4 | 最终**露出中心黄色花蕊** | 末帧花心确有黄色雄蕊 | **正确，细节级** |
| 5 | **完整开花过程** | 150 帧一镜到底，0 处场景切换 | **正确** |
| 6 | **延时摄影** | 一朵真花在 5.06 秒内完成开花，物理上只能是延时摄影 | **合理推断，非编造** |
| 7 | 类似**马齿苋花 / 太阳花** | 肉质叶 + 粉紫叶缘 + 红橙花，形态即 Portulaca 属（马齿苋科） | **正确，物种级** |

**不可能出现的词：0 个**（`IMPOSSIBLE_TOKENS` 覆盖人物 / 舞台 / 街道 / 动物 / 厨房一类主题）。
**可能出现的词：6 个**（花、花瓣、红、开、绽放、苞）。

### 诚实保留（两条）

1. **描述准确但不穷尽**。69 字摘要没有提粉紫色叶缘、深色虚化背景、绿色茎——**遗漏不是错误**，但这确实是「摘要级」而非「逐物级」的描述。
2. **「延时摄影」是推断**，不是画面里能直接看到的元信息。它是对的（否则真花不可能 5 秒开完），但它仍是一次推断，记录下来以免把它读成「读到了元数据」。

## 6. 为什么这次不一样（与历史失败并列看）

| 素材 | `success` | 返回的描述 | 判定 |
| :- | :- | :- | :- |
| 1 MiB `0x11` 填充 | true | 虎斑猫 / 紫洋葱 / 萨摩耶（三次三个动物） | **编造** |
| 64×64 1 s **纯黑**合成 | true | 「舞台杂技 / 钢管舞表演」，或「整段是黑屏」 | **编造或退化为空** |
| **真 · flower.mp4（本次）** | true | **一朵红花从紧闭花苞开到露出黄蕊** | **准确** |

**这三行放在一起才构成结论**：

- `success:true` 是**必要不充分**条件——它对无信息的字节同样返回 true，所以**不能单独作为「读到了」的证据**；
- 但**画面里真有信息时，模型确实读了**——而且读到了**时间变化**（花在开）和**物种级细节**（马齿苋花、黄色花蕊），这不是从 prompt 能猜出来的；
- 因此历史失败的正确读法是：**「没有可读内容 → 模型编造」**，而不是 **「模型无论如何都编造」**。这是与之前报告不同、且更重要的一条。

## 7. 边界：本次**没有**证明什么

| # | 未验证 | 为什么 |
| :- | :- | :- |
| 1 | 其它视频是否同样准 | **只测了 1 段、1 个 prompt、1 次调用**（纪律要求）。这是存在性证明，不是普遍性证明 |
| 2 | 长视频 / 多镜头 / 有字幕 / 有人脸 / 剧烈运动 | 本次素材是 5 s 单主体静态机位 |
| 3 | 细节问答（如「花蕊什么颜色」） | 本次只发了一个开放式描述 prompt |
| 4 | 第 3 步是否计费 | 未读额度；且既有报告已证明该额度接口对这类消耗看不出变化 |
| 5 | 大文件上限（>40 MB） | 本次 1.1 MB，远低于 40 MB |
| 6 | 同一段视频重复调用是否稳定 | 只调一次，无法评估方差（垃圾字节那几次的方差极大，真视频的方差未知） |

**特别提示**：§6 的三次垃圾字节结果**方差极大**（同素材三个不同答案）。所以「真视频描述准」这一次结果，**不能**推出「真视频描述每次都准」。要回答稳定性，需要多次调用——与本次「只理解一次」的纪律冲突，故留作开放项。

## 8. 对现有实现的含义（**本次不改 `src/`**）

> 只陈述实测事实指向哪里，不做修改。

| # | 位置 | 现状 | 实测结论 |
| :- | :- | :- | :- |
| 1 | `video-tool.ts` 上传路径 | 注释把 `success:true` 的保真度保留写成「未知」 | **本次给了正面证据**：真视频 → 准确描述。保留可以收窄为「对无信息内容会编造」 |
| 2 | 上传路径的容量假设 | 只测过 1586 字节 | **1.1 MB 实测同样可用** |
| 3 | `transport: "upload"` 的 opt-in 标注 | 因 fidelity 未知而保持 opt-in | **支持改为可默认使用**：链路通、字节一致、描述准 |
| 4 | 工具描述里「描述质量取决于服务端取回行为」的措辞 | 为垃圾字节的编造而写 | **仍然成立但需限定**：风险是「内容不足时编造」，不是「一律编造」 |

**建议的措辞（仅供参考）**：把「上传路径的描述可能不可信」改成「**内容不足的视频（纯黑、噪声、无可辨主体）可能得到编造的描述；内容清晰的视频实测描述准确**」。这比原来那句更接近实测。

## 9. 原始证据与保密自查

探针把每一行日志同时写进 `%TEMP%/minimax-video-fidelity-probe-transcript.log`（本次 **97 行**），并把素材字节与抽帧图一并落盘，便于复核。

transcript 的关键行（逐字）：

```text
[probe]   clip bytes=1128375 sha256=0cd83d94...24451 brand="ftyp"
[probe]   http=200 content-type="video/mp4" content-length="1128375" bytes=1128375 matches-upload=true
[probe]   http=200 ... bodyBytes=432   (videos_understand)
[probe]   results[0].success=true  results[0].error=""
[probe] writes=1 understanding-calls=1 generations=0 (each at most once, nothing retried)
```

**保密自查**（脚本内固化为 `scrub()` + `redactUrls()`，逐字沿用既有探针）：

- 令牌：只报 `<present:len=60>`，从不打印。
- 邮箱 / UUID / JWT / 32+ 字符不透明串：`scrub()` 清除。
- **账号 id**：`oss_key` 与 `cdn_url` 路径里嵌 `u<18 位数字>`，短于 32 位阈值，由 `\bu\d{12,}\b → <user-id>` 规则替换（transcript 第 34 行可见 `<user-id>`，规则生效）。
- **URL 值**：`oneLine()` 先经 `redactUrls()`，签名 URL 的 query 里就是凭据，一律换成形状。
- `x-oss-request-id`：只打印前 6 字符 + `...(truncated)`。
- 本次**没有**任何 `task_id` 出现在任何响应里。

**一处如实说明**：探针的 scratch 目录取自 `os.tmpdir()`。在本次运行环境里该值曾解析成相对路径 `undefined/temp`，会在仓库内生成杂散目录；探针已加 `resolveScratchDir()` 守卫（只接受绝对路径），此后落盘位置为 `C:/Users/A/AppData/Local/Temp/...`，**工作树内没有新增任何运行产物**。
