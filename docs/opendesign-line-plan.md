# OpenDesign line — integration plan and evidence

Status: implemented, mock-verified. The device-authorization contract was **probed live** (2026-10-21, quoted below); the approval frame's field names are cross-checked against upstream issue [nexu-io/open-design#8870](https://github.com/nexu-io/open-design/issues/8870). No human approved a probe authorization, so the approved frame itself is inferred from the pending frame's shape plus that issue — the reader keys on key presence, never on a status string, which is exactly what makes that inference safe to ship. No chat call against a real key was made.

## 1. What the line is

OpenDesign ([open-design.ai](https://open-design.ai/), open source at [nexu-io/open-design](https://github.com/nexu-io/open-design)) sells subscription plans (Go/Plus/Pro/Max) whose model credits third-party tools spend through the "OpenDesign API". The official pricing FAQ names the consumers verbatim: "Use an OpenDesign API Key with Codex, Claude Code, DSH, OpenCode, or Hermes."

## 3. Decisions

1. **Two sign-in paths, one pool.** Device authorization is the primary (it also yields identity + balance reads); a pasted console key remains as the documented fallback. The card's account heading holds exactly the two entries (the shared card's two-button rule).
2. **The host never opens a browser.** `/login/start` answers the activation URL and launches nothing; the card `window.open`s it (pinned in `test/login-opens-browser-once.test.ts`).
3. **Completion is read from the payload's shape.** `runtimeKey`/`controlKey` present = approved; a non-pending status with no keys = refusal, reported in the service's words. A 200 with null keys is pending, never a credential. A cancelled flow never persists a late-arriving approval.
4. **Quota is the billing summary's plan + credits, not a percentage bar.** The paid tier and the remaining subscription/top-up credits come from `/billing/summary`, read together with the wallet. The section states each figure the service sends (plan, state, period, credits and their USD companions, consumed today and total); no percentage is invented, because the summary states what is left but not the grant it is a share of. The wallet figure stays the spendable number on the account row and the composer badge, and the badge turns red only at exactly $0 (a spent balance is a fact; a threshold is not). The device-authorization `user.plan` is a profile flag that answers `free` for a paid account and never refreshes, so a billing read overrides it wherever the pool is projected, and the card reads the summary once when it opens rather than waiting for a click.
5. **Billing failures never mark an account.** Upstream maps billing refusals to 403 (OPEND-3553 in the open-source repo), so a wallet 401/403 is rendered as "unavailable" data and the chat credential keeps serving.
6. **A catalog sync announces only a real change** (id-sequence fingerprint compare before/after), and runs behind a sign-in or key add rather than on a poll loop.
7. **The fallback table and the whitelist share one id vocabulary** (the gateway's wire ids), so a cold-start filter cannot empty the picker; `[]` still wins in both phases. Synced catalog entries persist in the settings document — the warm path is a local read.
8. **The reasoning ladder is per model and sourced like the windows**: each row publishes its own ladder (e.g. `none/low/high/max` for DeepSeek, `low/medium/high/xhigh/max` for the Claude and GPT-6 families), the command-code registry's `off` is translated to DSH's `none`, and a model no source documents keeps the OpenAI trio as a *default* rather than being declared a non-reasoner. A row whose source publishes no ladder keeps the default trio and is **never** declared a non-reasoner: an empty ladder states that no source names levels, not that the model does not think. **Reversed 2026-11.** Three rows shipped contradicting that rule — `mimo-v2.6-flash`, `mimo-v2.6-pro` and `qwen3.7-max` carried `reasoning: false` on the strength of the command-code registry's empty `reasoningEfforts`, which cost them their thinking-depth selector entirely. The sibling `cline-pass` rows for the same families (`mimo-v2.5`, `mimo-v2.5-pro`, `qwen3.7-max`) say `reasoning: true`, and §2 makes the cline-pass DSH spelling the winner where the two disagree. All three now carry no `reasoning` field, so they take `DEFAULT_EFFORTS` (`low/medium/high`).
9. **The plan bounds what is advertised, but only after somebody measured it.** A successful sync persists the union of what the pooled accounts actually serve (`servedModelIds`); a model outside it is dropped from `listModels` and stays visible in the settings card, labelled "not in this plan". Three states, not two: never measured (`null`) advertises everything, measured-and-listed advertises, measured-and-absent does not. The picker rule lives in exactly one function (`line.ts`'s `openDesignVisibleModelIds`), which the adapter, the status projection and the hub card all read — a second copy would let the card's count disagree with the picker. Ticking a withheld row is the override and writes `forceVisibleModels`; that tick is *also* the row's checkbox state, because a row that read "checked" while the adapter refused to advertise it would contradict itself. Three details worth keeping: a sync where every account succeeds but every listing is empty is treated as a **failed read** (previous measurement kept) rather than "this plan serves nothing", which would hide the whole table; `visibility: none` and `all` clear the force list while `invert` (a per-row flip) does not; and an explicit selection prunes the force list, because the client's un-tick path only ever sends `enabledModelIds` and never `{visible:false}` — pruning at the selection write is what keeps the two in step without a client change.
10. **Settings writes are serialized.** Every mutator derives a WHOLE document from the one it read, so two in flight at once each erase the other's fields — and that is not hypothetical here: the catalog sync is fire-and-forget, so it really can land between a selection change's read and its write. `OpenDesignModelSettingsStore` now runs each mutation's entire read → compute → write inside one turn of a `Promise` queue, and the public `write()` keeps a `writeUnlocked()` body for the mutators to call so no operation ever queues behind itself. The queue's tail never carries a rejection: a failed write rejects its own caller and the tail is flattened afterwards, so one failure cannot poison the writes behind it. `read()` deliberately stays OUT of the queue (it is the hot path, and by the time a queued operation runs every write queued before it has already landed). Proven red-first: with the queue removed, an overlapping `storeCatalog` + `selectModels` pair deterministically loses one side's fields — the two red runs lost *different* fields, which is what "the last writer replaces the whole document" looks like — and the sequence test failed too. Residual, stated rather than hidden: the queue is per instance, so two processes writing the same file still need a filesystem lock that this line does not take.
11. **No sibling line was edited.** Shared additions are appends only: one id in `CONTROLLED_PROVIDERS`, one in `DIAGNOSTIC_PROVIDERS`, one hub entry, one brand entry, one locale/style/slot registration (badge at order 46), and one item in each existing count assertion.

## 5. Risks and left-unverified

- **~~The settings document has no write lock~~ — closed by decision 10.** The gap was real (the sync is fire-and-forget, so it could land between a checkbox click's read and its write) and is now closed by the store's write queue, proven red-first. What remains is narrower and stated on purpose: the queue is per instance, so two DSH processes writing the same settings file still need a filesystem lock this line does not take; `read()` is not queued, so a read taken mid-write sees the last committed document (never a lost update); and `readSync()` is superseded by the in-flight write's own cache assignment after its rename.
- **`servedModelIds` can never be written as `[]` by a sync**, by decision 9: a sync whose every account succeeded but whose every listing was empty is treated as a failed read, so the previous measurement stands. "Measured as empty" therefore only appears in a hand-edited document — which the settings reader still parses correctly, because the same three states are modelled on read.
- **The approved poll frame was never observed** (probing cannot approve itself). Mitigation: completion keys on `runtimeKey`/`controlKey` presence; the pending frame's null-key shape was probed live; the field names come from #8870. First real sign-in should confirm the account lands with email/plan populated.
- **The denied/expired poll vocabulary is unobserved** (a denial needs a browser). The reader treats any non-pending keyless frame as a refusal with the service's text, and 404/410 as terminal.
- **No chat call against a real key** — the mapping is pinned against the OpenAI shape and the gateway's probed 401 envelopes only.
- **The shipped windows are vendor facts, not this gateway's clamp.** They come from sibling tables of the same vendor models; a gateway may serve a smaller window, and an overstated one shows up as a context-length 400 on a very long conversation. Mitigations: the control-plane catalog (OAuth accounts) overrides them at sync time, the per-model editor corrects any row, and both beat the table. The one in-repo conflict (`gpt-6`/`gpt-5.6` family: 1.05M here vs 272k/384k in the ChatGPT-subscription catalog) is resolved toward the API-tier figure; OpenDesign's own price list prices a long-context tier **above** 272k input tokens, which independently shows the window exceeds 272k.
- **Two models no sibling table documents** — `minimax-m3.1-flash` and `muse-wonder` — keep the line defaults (128k, trio) until a live catalog or the user fills them; they are listed rather than guessed.
- **`POST /api/v1/oauth/token` (RFC 8628 device_code grant) appears in the open-source repo's tests but answered 404 live** — the current flow uses `{deviceId}/token` instead; the old path is recorded here so nobody "fixes" the new one into it.
- **Device-issued keys never expire** (per #8870, no expiry published or observed) and the console cannot yet list/revoke them — sign-out here is a local delete until upstream grows revocation.
- **Wrong-`deviceSecret` and post-expiry poll responses timed out during probing** (edge rate limiting, not observed verdicts).
- **The billing summary is account-scoped.** `/billing/summary` reports the personal workspace's subscription and credits; a paid team seat whose credits are attributed to another workspace was not probed. The card reports what this account's control key can read and does not synthesize a team figure.
- **The coding-plan windows live on a SECOND surface, found later.** `/billing/summary` prices the wallet and the credits but states no grant, so it can never answer "how much of the allowance is used". The console's own bundle names the endpoint that can:
  `GET {amr}/workspaces/{workspaceId}/billing/coding-plan-usage` with headers `x-vela-workspace-id: {workspaceId}` and the session credential, answering `{ tier, eligible, windows: [{ policyId, durationSeconds, remainingCredits, limitCredits, resetsAt }] }`.
  The console renders exactly two of those windows (its own filter): `durationSeconds === 604800` (7 days) always, plus `18000` (5 hours) on the `go` tier, and prints `remainingCredits / limitCredits` as "剩余 x%". Our card derives the complement, the used share.
  The path is REAL: probed 2026-10-22, unauthenticated → 401, while the earlier guesses (`/billing/windows`, `/billing/coding-plan`, `/billing/preflight`, `/usage/windows`) answer 404. Workspace ids come from `GET {amr}/workspaces` (also 401).
- **MEASURED 2026-10-22: that endpoint refuses every credential this plugin holds.** Probed live against the real Go account after the read was implemented, three shapes in order, same URL and same `x-vela-workspace-id`:
  `Authorization: Bearer <vela_ctrl_…>` → **401**, `Authorization: Bearer <sk-amr-…>` → **401**, `x-api-key: <sk-amr…>` → **401** — the refusal reads `HTTP 401: unauthenticated (tried: bearer control key; bearer runtime key; x-api-key runtime key)`.
  The workspace id RESOLVED during those probes (`GET /workspaces/current` answers `activeWorkspaceId` to the control key), so the 401 is the coding-plan route itself refusing the key, not a bad address. The console authenticates it with the browser session (`credentials: "include"`); the official CLI gets the same windows through `vela billing preflight`, which runs on the separate `vela login` session.
  **Consequence:** a plugin holding only API keys cannot read these windows. The read stays implemented (it lights up the day upstream accepts a key, or a session-capable caller fills `codingPlan`), the card says the real reason in one sentence instead of drawing a fabricated bar, and the settings card tells this refusal (console-only) apart from a workspace that genuinely configures no window.
